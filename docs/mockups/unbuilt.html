MOCK-UP Boxes you or an AI add to the map by hand. Two kinds: Planned (a class we intend to build, mostly for planning) and Added manually (real, but the scanner can't see it: loaded by name, generated code, an outside service). Sample data is the real Coderstanding map at level 1 Systems (7 of its 22 classes, hints as saved, some lines left out); the planned boxes are believable next features (node_store would keep these very boxes; issue_log is an AI draft). Nothing here is built. It reuses notes.jsonl, the card stages and priorities (7a), status/tags (12a), AI drafts + Accept, and the loaded-by line style (9b).

How each look reads

  • Planned: dashed outline and hatched header in the plan colour, hammer tab "Planned", name in the plan colour, no ▶ (there are no functions to open yet). Chips: stage, work:/imp:, tags, linked spec §. Footer says "not in the code yet" instead of a size.
  • AI draft of a planned box: same look, outline and tab in the AI-draft pink, "AI draft" chip, Accept in the panel (as AI notes today).
  • Planned lines: dotted, plan colour, a hammer disc in the middle. A planned line may touch a real class (server will save to node_store).
  • Added manually: double outline and hand tab "Added manually", footer = where it lives (file or service) or "where: unknown". Its lines are solid (the code really does it) with a hand disc in the middle, the same idea as the dashed loaded-by line (9b).

    7Storage (design only)

    They live in notes.jsonl, like every other hand-written fact: a node:<name> line with a new field made: "planned" | "manual", plus the fields notes already have (hint, description, tags, status, rules, level, domain, by, ai) and the card fields stage, priority, importance (same words and stage list as specs), spec (a spec id), where (manual only). Lines are edge:A→B lines with made too (planned: drawn dotted; manual: solid, like loaded_by). Example: {"key":"node:node_store","made":"planned","hint":"Keeps the boxes people and AI add by hand…","stage":"todo","priority":"high","tags":["planning","map"],"spec":"hand-added-boxes","by":"you"}. Because notes are never part of a scan, they survive every rescan untouched; the view engine adds them as nodes after the scan (one step in compute_view, the way Notes.loaders adds loaded-by lines), so the viewer, slim text and Copy for AI all get them from one place. A rescan only compares names: a made: planned node whose name is now a real class id gets built_now (the section 5 banner); Merge just deletes the made field (and drops stage/priority/spec into the linked spec's history), so the existing notes attach to the real class with no copying; Keep both renames the key to node:node_store (planned). Ids never collide with scanned ids, because a write is refused while a real class has that name. Lost-notes logic (section 10) ignores made nodes, since they're not supposed to be in the scan.

    Open questions

    1. Stage on the box or on its spec? The mock lets a planned box carry its own stage/priority (handy for small things with no spec). The other option: a planned box always links a spec and shows the spec's stage, so there's one stage per piece of work.
    2. Merge on an exact name match: always ask, or merge silently and just say so in the scan note? And should a close name (word matching, e.g. NodeStore for node_store) also offer the banner, or only "It's built: pick the class…"?
    3. One system with loaded-by? A manual line and a loaded-by line (9b) are both "a real link the scanner can't see". Fold loaded-by into manual lines (one style, one store), or keep loaded-by as its own thing?
    4. Default for "Show planned work": Show (as mocked) or Hide until you switch it on? And remembered per project?
    5. Can a planned box have planned functions (rows you open with ▶, e.g. node_store#add) that tours and specs can link, or is that too much for now?
