MOCK-UP Ideas to make the map readable at a glance, for someone who builds code with an AI and wants to understand it. Sample data is the real Coderstanding map, level 1 Systems (12 of its 22 classes, hints and descriptions as saved). Nothing here is built. Tours highlighting / popup notes and auto-layout alignment are other work; section Fit says how these ideas meet them.

What "readable" means: checkable goals

In 30 seconds, a newcomer can say…

  • what the app does, in one sentence;
  • its 5–9 big parts and what each is for;
  • where it starts (which box runs first);
  • what a box means and what a line means, without opening the legend.

In 5 minutes, they can…

  • follow one main flow end to end (e.g. "how a scan works");
  • pick any box and explain what it does and who uses it;
  • tell explained lines from plain "uses" lines;
  • find the class behind a feature by name or word;
  • know the jargon on screen (level, domain, via, hub).

Today (screenshots of the real viewer)

  • Boxes say 30 functions · 0 fields, not what they do.
  • Domain frames say double-click to show only it.
  • 10 line kinds in the legend, UML names, all shown even when absent.
  • ~35 lines at level 1, most are bare [dependency], same weight as explained ones.
  • Two rows of ~20 controls before the map.

  • 30-second overview story of the domains
  • Start here: numbered main path from the entry point
  • Calm toolbar with presets
  • Glossary hovers for jargon
  • Importance cue on boxes (used by N, size)
  • Search-first landing page
  • Guided first run (coach marks)
  • Breadcrumbs "Domain › class › function"
  • Colour = domain everywhere (box strip, chip, frame)
  • Hide outside code until asked
  • Box size by importance
  • "Ask AI about this box" button
  • Matrix view (DSM) for big maps
  • Diff view: what changed since last look
  • Sequence strip for one call chain
  • Readable labels: no truncated hints on lines
  • Level names as questions ("What are the parts?")
  • Read-aloud summary of the map

1

Say what each box does

value higheffort low
What

The box face shows the class's one-line description under its name. Counts move to a quiet footer, with a small "how much it matters" cue.

Why

A map of names only asks the reader to know the code already. The descriptions exist (code header or note hint); they just sit in the details panel.

How

Box text setting: Name / Name + what it does (default) / Full. Wraps to 2 lines max, using the existing name/sub-line wrapping. No description → "No description yet" with Ask AI. Domain frames show the domain's description instead of the click hint.

2

Explained lines first

value higheffort low
What

Lines that have a hint ("Rescanning a project runs the scanner") are drawn full; bare [dependency] lines are drawn thin and faint until you hover or select one of their ends.

Why

At level 1 most lines are unexplained "uses" lines. Drawn at the same weight they bury the 18 that tell the story.

How

A Lines switch: Explained first (default) / All equal. Hover a box: its faint lines come back. The count shows what is faint, so nothing feels hidden. It also gives the AI a clear job: explain the faint ones.

Lines

Extends the View engine Show switches (a show["lines"]="explained" flag marks edges quiet, so Copy for AI and coderstanding graph can sort explained lines first too) and the wire drawing in app.js (the existing .lines.quiet style). No new component.

3

Plain-words legend + line hover

value higheffort low
What

The legend lists only the line kinds on screen, in plain words first ("uses", "goes through hidden classes"), the UML name small after. Click a legend entry to light those lines. Hover a line for one sentence.

Why

Ten UML terms up front (realization, association…) are a test, not a key. Most views use 2–3 kinds.

How

Legend built from the view's edge kinds. Line hover sentence = "A verb B: hint", e.g. "cli uses offline: Every command switches on the offline guard first". Tap works on phones.

On this map:

Hover (or tap) any line.

Extends the Viewer legend (built from the view, not fixed HTML) and Field rules (field_help.js): the plain words per kind live in one table there, which the legend, line hover and glossary (idea 8) all read.

4

Focus + "In plain words" panel

value higheffort medium
What

Click a box: everything not directly connected fades, and the details panel opens with sentences, not fields: what it does, who uses it and why, what it uses and why, where it sits.

Why

Answers "what does this do and how does it fit" in one look. Today the panel starts with help text and lists of names.

How

"In plain words" is the top block of the existing panel; the current lists stay below under "Details". Unexplained links get an Ask AI button (makes a hint draft, as notes already allow AI drafts).

Extends the Viewer details panel and Details-panel lists (lists.js folds long lists), the existing .dimmed style and neighbour focus (test_focus_neighbours); the same fade is what tours use to highlight a step, so both share one "focus set" helper.

5

30-second overview

value medium-higheffort medium
What

Level 0 opens as a short story of the domains, one sentence of flow, then a card per domain: what it is for, its key classes, who it talks to. "Show on map" opens the frames view.

Why

The first question is "what is this app made of?", and prose answers it faster than 20 boxes and 30 bundled lines.

How

Built from what exists: domain descriptions (new note field on the domain), level 0 lines and their hints, hub/size for "key classes". The flow sentence is a note too (AI drafts it, you edit).

Extends Domain frames (domains.js data, same order and colours), Notes store (a description on domain:<name> keys, like class notes) and Slim text (the same overview prints in coderstanding graph <app> 0, so the AI reads what you read).

6

Start here: the main path

value higheffort medium
What

A "Start here" button numbers the main flow on the map from the entry point: 1 → 2 → 3 …, each step a box and the hint of the line that leads to it. A second path for the other main flow.

Why

A newcomer doesn't know where to start reading. A path through 4–5 boxes gives the spine; everything else hangs off it.

How

A start path is a short tour flagged start: no new store. The AI drafts it from the start badges and the strongest hinted lines; "Play as tour" opens the full tour.

    Extends Tours (tours.py item store, a start: true front-matter flag; the Tours tab draws the badges) and Entry kinds (the start badge picks step 1). The step highlight is the tours highlight being built now.

    Calm toolbar with presets

    value mediumeffort medium
    What

    One row: tabs, the level ruler, a search box, and a preset: Read / Explore / Edit. Every other switch goes under "More options" and shows which ones the preset set.

    Why

    ~20 controls before the map tell a newcomer this is hard. Most visits want one of three set-ups.

    How

    A preset is just a set of the existing switches (same as the URL options). Changing any switch shows "Custom". Remembered per project like the domain switches.

    8

    Words explained

    value mediumeffort low
    What

    Jargon on screen gets a dotted underline; hover or tap shows one plain sentence. A "Words" list sits in the help.

    Why

    The CLI text and the viewer use terms like via 2, hub, level, domain, outside code, that are clear to us and not to a newcomer.

    How

    One glossary table (with idea 3's line words) in the field-help data; a small helper wraps known terms in labels and panel text.

    Extends Field rules (field_rules.json → field_help.js): it already holds the help text for note fields; terms join it so there is one place for wording the viewer and the AI guide share.

    Fit with work in progress

    • Tours highlighting / popup notes: idea 6 is a tour with a flag, so it gets the highlight and popups for free. Idea 4's fade and the tour step highlight should be one focus helper; the popup note can show the same "in plain words" sentence as the panel.
    • Auto-layout alignment: idea 1 makes boxes taller (up to 2 description lines), so alignment must use real face heights. Ideas 2 and 6 read best when the main path lines up left to right; the start path could be a layout hint ("keep these in one row").
    • Order: 1–3 first (small, independent, big win), then 4 and 6 once tours highlighting lands, then 5, 7, 8.
